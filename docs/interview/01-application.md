# 01　组装入口：一句任务怎样交给各个模块

假设工作区里有一个 `parser.py`，你想让程序补上空输入处理，并运行测试。你在终端输入：

```bash
pycode --workspace /project --providers providers.json -p "给 parser.py 增加空输入处理，然后运行测试"
```

这句话已经说明了要做什么，但程序还不能马上把它交给模型。它还需要知道：到哪个目录读文件、使用哪家的模型、把对话存在哪里，以及模型提出读文件或运行命令时由谁执行。

这一章就从这条命令往下读。先看这些信息怎样凑齐，再看任务怎样交到真正运行 Agent 的地方。沿途出现的类名，是为了让你在代码里找到负责的人，不需要先把它们背下来。

## 第一步：先确定文件、配置和历史放在哪里

终端首先进入 `cli/main.py` 的 `main`。它拿到的是一串参数，例如 `--workspace /project`，因此先请参数解析器把不同选项分开，再把目录和开关交给 `load_config` 与 `AppConfig` 检查。示例使用了 `-p`，`main` 接着把它转换成 `run` 命令，并把后面的文字放进 `args.prompt`，后面就能选到负责执行任务的 `execute_run`。

这里最重要的是两个目录。`workspace` 是这次允许处理的项目目录，例子里就是 `/project`；`user_data` 是程序保存会话、模型请求记录等数据的地方。两者分开，程序就能修改用户指定的项目，同时把自己的运行记录放到固定位置。

检查后得到的 `AppConfig` 可以理解为“这次工作的设置单”。后面的模块读这张设置单，不必再各自解析一遍终端参数。比如沙箱开关和允许传给命令的环境变量，都在这里先检查，再交给实际执行的模块。

到这里，程序已经知道去哪儿工作，但仍然缺少模型的连接设置。`providers.json` 保存模型名称、服务地址和密钥对应的环境变量名。`command` 读这个文件，得到后续创建模型客户端要用的信息。真正的密钥不需要写进对话记录。

## 第二步：有了设置，把需要的功能接到一起

现在再看 `compose_application(config, providers)`。传进去的两项分别是刚才的工作设置和模型配置。它返回一个 `Application` 对象，后面的代码通过这个对象请求“打开会话”“查看模型”“创建界面”等能力。

为什么需要这一层？因为终端和 TUI 都会用到这些能力。让它们从同一个入口取得能力，就能使用同一套文件权限、会话记录和工具执行规则。读代码时，你可以先把 `Application` 当作“应用能做哪些事的入口”，暂时不追它内部所有的类。

`compose_application` 还要决定用哪一组功能模块。正常启动时，它调用 `default_modules`；如果调用方已经明确传入替换过的模块，就使用那一组。这里保存的是模块对象和以后会用到的创建方法，还没有把用户的修复任务发给模型。

接线也不只是把十四个名字放进列表。例如，Skills 需要读取指令文件，还可能运行 Python 资源，因此组装时要把文件读取的方法和受限制的进程执行方法交给它；Hooks 也能执行动作，但仍要使用统一的工具检查。这样，各模块能配合工作，而不用自己再寻找另一套执行办法。

下一节才会真正打开一个会话。先记住这次调用的结果：我们有了一个知道“使用哪些模块、怎样找到它们”的 `Application`。

## 第三步：打开会话，把后面会反复使用的东西准备好

用户这次修复可能不止发一句话：模型可能先读文件，再询问一次批准，之后运行测试，用户还可能继续补充要求。这些内容需要归到同一段对话里。因此 `command` 接着调用 `Application.open_session`，取得一个 `AgentSession`。

打开会话时，程序会先打开保存历史的文件，检查上次有没有留下未确认的工具结果，再准备计划、记忆、Skills、MCP 等当前启用的能力。它还会创建负责开始、暂停和结束本轮工作的对象 `SessionLauncher`，后文简称 launcher。

launcher 此时拿到了一些“需要时再调用的方法”。例如，真正开始一轮工作时，它会调用 `build_configured_run`。组装代码先把这个方法交给 launcher，而不是让 launcher 自己去寻找所有功能模块。后面换用别的模块实现时，这条调用路径仍然能保留。

这一步完成后，返回给 `command` 的是一个可以接收用户消息的会话。目录和模块已经选好了，历史也打开了，接下来才轮到“修复 parser.py”这句话。

## 第四步：把用户的话交给会话，再开始本轮工作

`command` 根据命令名称找到 `execute_run`。后者把文本包装成一条用户消息，交给 `AgentSession.run`。这条消息除了正文，还有一个输入 ID，用来区分这是新任务，还是同一输入被重复提交。

`AgentSession.run` 先进入该会话的执行锁，再由 `_run_locked` 检查输入和当前分支。它会把用户消息写入历史，追加一条 `run_start`，记录“哪条输入开始了哪次工作”，然后调用 launcher。这样，程序在真正修改文件之前，就已经留下了能够解释这次工作从哪里开始的记录。

launcher 接着调用前面保存的创建方法。`build_configured_run` 为这一次工作准备 Skills、MCP 和继承下来的工具声明；`build_runtime` 再把模型、工具执行、上下文处理等能力接好，创建 `AgentRuntime`，放进 `RuntimeContainer` 返回给 launcher。注意，此刻返回的是准备好的运行对象，执行图还没有建立。

下面这条链把前几节接起来了。先顺着每步上方的说明读，理解为什么要进入下一层；想核对实现时，再展开对应函数。

## 第五步：完成、等待和退出，分别保留什么

一次工作通常会包含几次模型请求和几次工具调用。`build_runtime` 返回的 `RuntimeContainer` 把这次工作使用的对象放在一起，使 launcher 能在结束时找到它们并关闭连接、等待后台工作停止。

如果组装到一半就失败，还没有拿到完整的 `RuntimeContainer`，怎么办？创建每项资源后，`AsyncExitStack` 就会记下相应的关闭方法。后面某一步失败时，它依次执行这些方法，避免模型连接或后台任务遗留。这个对象负责的是“尚未组装成功时的清理”，而不是用户任务的执行。

正常完成后，一轮工作里临时创建的模型等对象可以关闭。有些对象还要给后续对话继续使用，例如摘要和 Hook 的后台任务，它们由 launcher 继续管理，到整个会话关闭时再收好。因此代码里要区分“一轮结束”和“用户退出会话”，不能把两者当成同一时刻。

等待用户回答还要再分情况。同一进程的 TUI 可以保留当前执行图，收到审批答案后继续；非交互 CLI 遇到 `needs_input` 会以退出码2结束并关闭会话。之后启动的新进程只能读到保存的历史，不能复活上一个进程里的执行图。

## 回头看：十四个模块分别替这次任务做了什么

前面走的是调用顺序，下面这张表用于查“某件事归谁管”。它不是要求你从上到下依次调用十四个模块。实际开启哪些能力、什么时候创建连接，要看本次操作和配置。

## 框架在本模块怎么用：它们对应的是刚才哪些动作

第一步里的参数解析交给 `argparse`；Provider 文件用 Pydantic 的 `TypeAdapter` 检查字段和类型。它们解决的是“把外部输入变成可以使用的设置”，不会替我们决定某个会话应该打开哪些模块。

把同步终端入口接到异步命令处理，用的是 `asyncio.run(command(...))`。这里的异步，是为了让等待模型、等待进程输出和界面更新能够配合进行；一次调用 `asyncio.run` 并不代表只会有一次模型请求。

前面说“把以后要调用的方法先交给 launcher”，代码中经常用 `functools.partial` 完成：它先固定一部分参数，等真正开始工作时再补上本轮参数并调用。读到它时，先问“这里是在保存方法，还是已经调用了方法”，就不会把组装误读成已经执行任务。

第五步的失败清理使用 `AsyncExitStack` 安排已创建资源的关闭顺序。至于 deepagents、LangGraph、LangMem 和 MCPAdapter 的使用，则留在各自功能内部。组装入口只接上这些能力，不在这里重写它们的工作流程。

## 读到这里，再检查几个容易误会的地方

**打开会话就已经把任务发给模型了吗？** 没有。打开过程是在准备历史和所需能力，用户消息由后续的 `execute_run` 交给会话，launcher再开始本轮工作。打开过程本身可能需要发现模型或连接已启用的MCP，不能因此把它等同于模型已经回答用户任务。

**为什么一处关闭失败，还要继续关后面的对象？** 它们可能分别持有连接、进程或文件写锁。前一个报错不应让后面的资源无人处理，所以代码会继续尝试，最后再把错误返回。

**保存了等待记录，为什么不能在新进程回答旧审批？** 历史文件能说明当时在等什么，但旧执行图和客户端对象属于已经结束的进程。新进程不能只凭一个旧答案重新执行可能改文件的操作。

**怎样判断组装是否真的分开了？** 读 Skills 或 MCP 的 `module.py` 时，应当能看到它需要什么、创建了什么、把什么交回应用。再回到 `default_modules`，可以看出这些输入来自哪里，而不是到许多文件里猜依赖。
