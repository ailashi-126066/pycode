# 06　读 parser.py、改文件，再把结果交回模型

上一章停在这里：用户说“修好 `parser.py`，然后跑测试”，模型已经决定先调用 `read`。模型发出一个函数名和参数，并不会自己打开磁盘。接下来要回答的是：谁真的读文件，谁允许修改，修改之后又是谁告诉模型“这一步确实完成了”？

我们跟着这次任务走一遍。先不要记模块名，把它看成一段往返：模型提出动作，程序检查并执行，把结果保存好，再交给模型决定下一步。

工具发现由公共 ToolSearch 负责：本地和 MCP 工具共用分类简表。exposure=direct 的工具（Pi 的 read、bash、edit、write、grep、find、ls，以及 ToolSearch、任务板和子 agent 工具）每次都带完整定义；其余工具按名字或关键词匹配搜索，不调用模型、不执行目标工具，结果成功保存后在下一轮提供完整定义。执行时只检查调用名在不在本次请求的工具列表里。

## 第一步：先读到一个确定的文件版本

模型请求 `read("/workspace/parser.py")`。这里的 `/workspace/` 是程序给模型看的路径，不是要求机器上真有一个同名目录。内置的 read 工具（`tools/adapters/builtin/read.py`，照 Pi 的 read.ts）把相对路径解析到 `/workspace/`，再经 `CompositeBackend` 的挂载表找到工作区后端 `PycodeBackend`。

后端的 `aread` 把实际读取交给 `read`，让文件I/O不阻塞其他异步任务。`read` 第一件事不是 `open`，而是调用 `resolve`：去掉挂载前缀后的虚拟路径必须留在工作区，不能穿过 `..`、目录链接或进入 `.git`、`.pycode`、应用数据目录。这样模型虽然给出了路径，却不能自己决定机器上哪里都可以读。

路径确认后，`read` 在同一文件的锁内计算摘要、读出有界内容，再算一次摘要。两次一致才把这个版本记在 `receipts[path]` 中。这张小记录接下来才有用：模型读完后可能思考几秒，用户也可能在编辑器里改文件。等模型要求 `edit`，后端的 `check_version` 会拿当前摘要和刚才的记录比较；不一致就要求重新读，不能覆盖用户后来写入的内容。

`write` 和 `edit` 都复用这条检查。`edit` 还会确认每个 oldText 确实存在且只匹配一次；同一文件的修改经文件修改队列排队，不同文件之间并行；确认要改的是同一版本、同一位置后，才通过临时文件替换目标。读到内容并不意味着获得修改许可，真正的批准还在下一步。

下面是三个由框架分别进入的文件操作入口，不是 `read` 执行完就自动调用 `write` 和 `grep`。搜索也使用同一组路径限制，并在把文件名交给 rg 之前限制搜索范围。

## 第二步：模型决定编辑，程序先问“这次能不能改”

假设模型已经看到错误，要求把 `parser.py` 的一个分支改掉。程序先查这条调用是否属于本次模型真正看过的工具集合。不存在的名字返回 `unknown_tool`；名字不在本次请求工具列表里的调用（例如没有先用 ToolSearch 加载）被拒绝为 `tool_not_declared`。这时不会为了一个不该调用的工具再弹批准框。

通过这一关以后，`ToolExecutor` 先校验参数，再进入已经组装好的权限检查。普通读操作可以直接继续；修改和外部操作通常要等待用户。`InterruptToolGate.authorize` 生成包含本次操作ID、参数和工具定义摘要的问题，交给 LangGraph 的 `interrupt` 暂停当前图。因此批准以后恢复的是刚才停住的调用，不是重新猜一次模型想做什么。

这也是为什么批准框必须带操作身份。用户如果批准的是旧的编辑，就不能把这份回答拿去执行另一条命令。`AgentRuntime.resume` 会核对当前图真正等待的问题；图已经丢失、问题已经结束，或回答不匹配，都不能继续旧操作。

还有两个容易漏掉的分支。Plan只允许写当前计划文件时，编辑 `parser.py` 会得到明确拒绝；非交互模式下的子 agent 用只读门，需要审批的调用直接失败。嵌入方提供的 custom 门和 Skill 的 allowed-tools 范围包在默认链外层，先判断再交给默认链。这些限制是组装权限检查时接进去的，不是靠模型自觉遵守提示词。

## 第三步：获准执行，还要把结果保存好才算结束

现在编辑可以运行了。沿调用链往回看，程序在执行任何工具之前，已经先保存了那条完整的assistant消息，里面包含本次调用ID。`ToolSettlementMiddleware` 是框架调用工具前后会经过的中间件；它先确认这个ID确实属于刚保存的消息，再把动作交给 `ToolExecutor.execute`。

执行器负责共同步骤：参数校验、前置Hook、权限、需要时拍文件快照，然后才调用实际工具。内置工具处理文件，bash处理命令，Skill和MCP处理各自实现；这些差异没有改变共同入口。每个调用的 `ToolCallState`（issued→validating→awaiting_approval→running→settled）只由 begin 和 settle 推进；框架工具通过传入的 `invoke` 函数运行，这个回调只会在执行器检查通过后触发。

工具返回以后，执行器准备完整输出，并在有快照的情况下补上修改后的文件版本。但是，这时还不能通知所有人“已完成”：返回的结果仍需要写进会话。中间件把结果先放到 `ready_results`，再由 `settle_ready` 按模型原来的调用顺序保存。

为什么不谁先结束就谁先写？模型可能同时请求两个只读工具，后一个先返回。允许它们并行能节省时间，但历史和后续通知仍要有确定顺序。`settle_ready` 等到前面的结果也就绪，才调用绑定了当前会话的publisher保存工具消息。随后才能通知扩展，最后发 `tool_execution_end` 和后置Hook。

所以，“进程退出了”“完整输出写好了”“会话里有结果了”“界面显示结束了”是四件依次完成的事。任何后一步都不能代替前一步。

## 第四步：测试输出太长，模型怎么继续看

编辑成功后，模型请求 `bash("python -m pytest -q")`。下一章会跟着命令进入进程；这里先看它返回的结果。如果测试打印了几千行，不能全塞进下一次模型请求，也不能只留下最后几行就丢掉正文。

照 Pi，超过 2000 行或 50KB 时截断：read 保留开头，bash 保留结尾。完整输出写到 `$TMPDIR/pycode/<session_id>/<call_id>.log`，结果末尾写明显示的是哪几行和完整文件路径，details 追加 truncation 与 full_output_path。流式工具通过writer不断追加字节，结束时没超限就删掉文件、把全文放进结果。取消时明确记为 `interrupted`，不能把已有的半段日志当作完整成功。

## 回头看，框架和本项目各做了哪部分

Deep Agents负责模型和工具之间的循环，内置工具建在 Deep Agents 的 `CompositeBackend` 上，`StructuredTool`把普通工具的参数格式说明（schema）和异步函数交给框架。我们没有再写一个循环把 `tool_calls` 手动执行一遍，否则同一个编辑可能运行两次，也会破坏审批暂停。

本项目补在框架留出的入口上：`HistoryMiddleware`保存完整模型消息；`ToolSettlementMiddleware.awrap_tool_call`包住每次工具调用；`ToolExecutor`统一检查权限、输出和快照；结算后用 `Command(update=...)` 把配对的结果交回框架。

只读临时错误可以使用框架的 `ToolRetryMiddleware`，但写操作不能因为“可能没成功”就自动重做。`ToolErrorMiddleware`只把明确可恢复错误转成工具结果；存储错误、程序错误、图中断和取消继续向上交给对应处理者。错误文本还要隐藏密钥等内容，最多保留1600字，不能把校验失败时的密钥参数又存进结果。

## 这些函数是在哪里接起来的

`composition.runtime.build_runtime` 需要一套能执行本次任务的工具，于是调用 `ToolExecutor` 创建registry、文件后端、权限检查、输出存储和执行器。`composition.bindings` 再把消息保存函数、格式转换和结算中间件交给Agent。构造这些对象时没有执行编辑；真正执行仍要等框架收到模型的工具调用。

替换后端可以改变文件从哪里读，但不能删除执行器的检查；增加Skill或MCP工具，也只是把它们的处理函数接进相同流程。任务取消时Agent要收集已登记的工具任务，底层文件或进程函数则负责等自己的操作收尾。

## 如果这次修改没有顺利走完

**模型的工具参数只生成了一半呢？** 输出长度限制或解析错误会在执行前挡住，不能运行半截调用。连续三次相同工具、参数和错误仍没解决，后续会得到 `repeated_tool_failure`，要求换办法。

**用户在模型思考时改了文件呢？** 后端比较刚才读取的版本，变化了就重新读。这和批准是两件事：批准编辑，也不能覆盖一个从没看过的新版本。

**工具名是假的，或者这轮没有提供给模型呢？** 分别返回未知工具或未提供工具的拒绝，都不执行。未提供工具只能做只读拒绝检查，不能提前运行可能有副作用的 `before_call`。

**工具已经改了文件，after快照却存失败呢？** 程序抛出 `snapshot_settlement_failed`，不能当成普通失败继续，也不能说文件一定没变。下一步要核对实际效果。

**输出被截断是不是测试失败？** 截断只描述预览；退出码、错误状态和完整输出另存。模型可以用 read 读完整文件，不能靠预览最后一句推断全部日志。

**取消时文件或进程还在运行呢？** 上层先收工具任务，底层等待线程结束或结束进程组。取消意味着停止并核对，不意味着已经发生的修改自动回滚。

读到这里，可以用三个问题自检：为什么先保存assistant再执行工具，为什么有权限检查还要比文件版本，为什么工具返回后不能立刻发完成事件？它们分别防止无来源的效果、覆盖并发修改和重启找不到已宣告完成的结果。

接下来跟着 `python -m pytest -q` 继续往下看。工具执行器已经允许这条命令，但在机器上真正启动它之前，还需要确定进程能访问什么、超时后由谁把它结束。
