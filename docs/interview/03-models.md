# 03　把“修 parser.py”真正交给模型

上一章留下了一条有ID的用户需求，以及当前分支上应继续阅读的历史。它们仍是项目自己的`Message`，模型SDK还没有收到请求。现在应用需要把这段历史交给选定模型，让它决定先读parser.py，还是先查看已有测试。

这一章不从一张类名表开始。我们跟着这次请求走四步：准备可关闭的SDK对象，确认这次模型能看到哪些工具，保存请求并发送，最后处理同模型的有界重试。Agent框架何时回调这些方法，第05章会把它们接起来。

ModelCatalog 在接收 Provider 配置、生成或读取目录快照时冻结数据。snapshot 等读取方法共享这些不可变对象，避免每次读目录都深复制；进入 SDK 或 JSON 等需要普通可变数据的边界时，再做格式转换。

## 第一步：选好了Provider，为什么还不能直接发送文本

应用选定 Provider 后调用 composition.open_model。它用 AsyncExitStack 登记请求账本、同步与异步 HTTP transport 和自有事件 journal，再调用 create_model 选择官方 LangChain 集成。ModelOwner 保存模型、ModelRequestRunner、账本和关闭栈；本轮结束后 aclose 释放这些资源。

凭据在创建模型时由 credential_environment 解析，历史和缓存不保存真实密钥。OpenAI 与 DeepSeek 使用 httpx，Anthropic 当前依赖使用 httpx2；应用为每个 owner 创建 transport，避免关闭 LangChain 缓存中其它 owner 共享的客户端。

## 第二步：先提供工具简表，再按需加载完整定义

本地工具、框架文件工具和 MCP 工具都进入公共 ToolSearch 目录。主模型先看到按来源分类的名称和一句话用途，以及 ToolSearch、Pi 的 7 个内置工具（read、bash、edit、write、grep、find、ls）、任务板和子 agent 工具的完整参数。其余工具按需加载。调用 ToolSearch 后，程序匹配名称和描述，把结果的完整定义交给后续模型请求。整个搜索过程不调用额外模型。

搜索结果必须成功保存，才会加载工具。目录出现名字并不允许直接执行；未加载的调用被拒绝。已加载工具仍需要参数校验、只读与 Plan 检查、审批和执行前的 MCP 定义校验。

## 第三步：先记下要发的一次请求，再等待模型回答

请求进入`model_request_step`时，这个函数本身只是把方法包装成一个可组合步骤。代码用的是LangChain的`RunnableLambda`；只有随后调用这个步骤的`ainvoke`，内部闭包才会把请求交给`ModelRequestRunner.invoke`。读代码时不要把“创建步骤”和“已经发请求”混成一个时点。

Runner先拿锁，避免同一组SDK观察状态被内部并发请求覆盖。进入一次实际发送前，它创建`RequestRecord(status="started")`并写入SQLite。记录里既有会话和运行ID，也有这次逻辑请求的`logical_id`，以及实际尝试序号`attempt`。网络请求必须排在这次写入之后；账本写失败，就不能继续悄悄付费请求。

然后才调用框架传来的模型`handler`。SDK负责协议交互；Runner 读取 LangChain 返回的 usage_metadata / response_metadata，保存实际用量和响应身份，缺失值保持未知。没有 SDK 响应代理。完整响应返回后，Runner把记录改成已完成，保存Provider实际报告的token数量，再通知界面更新用量、结束本次请求。代码中的状态值是`completed`。还没结束的token片段由界面显示，不在这里伪造成一条已完成assistant消息。

## 单模型失败处理

失败只在所选模型内做有界重试，耗尽后报告错误。用户可以手动切换模型；不会自动启用备用模型。

## 回看这次请求：模块入口和框架各做了哪部分

应用配置本身不建立连接。一轮运行、工具选择、摘要和记忆整理各自通过显式模型工厂获取 owner，并记录 purpose。子工作区通过 child_config 派生数据路径；不存在模型模块 scoped 工厂。ReasoningDeepSeek 只补回官方集成未发送的 reasoning_content，OwnedChatAnthropic 只提供 transport 所有权，不观察或代理 SDK 响应。

SDK构造和协议差异在`create_model`中；同模型重试由官方中间件提供，工具发现由公共 ToolSearch 实现。项目增加的是实际请求前后的记录、错误分类、最终工具名单与“谁来关闭客户端”。所以这些框架类不是一个额外执行器名单，而是刚才四步中各解决一件具体问题。

| 现在回查代码 | 在故事中的位置 | 完成后交给谁 |
|---|---|---|
| composition.open_model / create_model | 请求之前准备SDK与账本 | 当前运行负责最后aclose |
| ToolSearch / calibration | 按需加载定义并计量请求大小 | 模型请求，以及之后的执行检查 |
| ModelRequestRunner | 先保存开始记录，再发送，最后保存完成或失败 | Agent的完成响应保存方法 |
| ModelFallback | 仅在允许失败后检查候选 | 同一业务请求继续，账本保留候选位置 |
| MeteredChatModel | 选择器、摘要、记忆等组件也要请求模型时 | 仍进入同一计费方法，不执行工具循环 |

缓存`model-catalog.json`只保存模型身份与能力。实际尝试保存在SQLite的`model_requests`；会话 Store中的工具集合和候选说明用于解释当时怎样执行，两者回答的问题不同。网络等待期间不持有一笔长SQLite事务。

## 读懂检查：如果这次修复请求出了问题

- **为什么关闭SDK内置重试，却仍能重试503？** 因为官方重试中间件重新调用Runner，每次实际请求都能单独记录。
- **logical_id和request_id为什么不能只留一个？** 一个标识模型轮次，另一个标识实际付费尝试；失败后再试仍是同轮，但不是同次请求。
- **选择器不开，为什么还要校准？** 最终工具名称和输入大小仍要绑定到真实请求，不能仅凭目录中有实现就允许执行。
- **搜索失败会全量发送工具吗？** 不会，返回空结果或错误，由模型调整查询。
- **后台模型为什么有单独用途和关闭方法？** 选择工具、写摘要与整理记忆都可能付费，不能混进主回复后丢掉请求或连接。
- **模型没返回用量，能否用估算补上账单？** 不能。估算供下一章判断容量，Models保留Provider已报告或明确未知的计费信息。

现在可以把问题从“这次模型请求有没有被正确发送和记录”，移到“模型下一次应该读到什么”。当读文件与测试结果不断增加，Context负责保留正确路线、解释容量，并在不丢原始记录的前提下缩短发送内容。
