# 13　记忆：下一次修代码，怎样还记得用户偏好
上一章已经让“修复 parser.py，并跑测试”成为可重新打开的会话记录。但下周打开另一条会话时，模型不一定会看到今天的聊天。用户想记住的是“解释先给最小例子，Python 测试用 pytest”，不希望每次把整段旧对话重新贴一遍。本章从这个缺口讲起。
```text
模型主动记：manage_user_memory / manage_project_memory → 一条一个 <id>.md
压缩被采用后：后台 LangMem 整理一次（另有手动 /memory extract）
下次任务：系统提示里放索引（每条一行）→ 模型需要时用 read 读 /memory/<scope>/<id>.md
```
做法和 Skill 一样：只给索引，正文按需读取。没有自动召回，也没有后台打分。
## 第一步：新任务开始，系统提示里只有一份索引
每个 run 开始刷新系统提示时，`MemoryService.prompt_index` 读出用户和项目两个作用域的记忆（项目作用域只在 `--trust-project` 时存在），交给 `memory_index` 拼成一段：开头说明这是数据而不是指令，后面每条一行 `[user|project] <id> — <description>`，按更新时间取最近 50 条。没有记忆时这一段不出现。
模型觉得某条相关时，用普通的 `read` 读 `/memory/user/<id>.md`。这两个目录是只读虚拟挂载，和 `/skills/` 用同一套机制，读取在进程内完成，沙箱不需要放开 `~/.pycode`。读到的内容是普通工具结果，由旧工具结果驱逐和压缩照常清理。另一路 `AGENTS.md` 是指令文件：Deep Agents 的 `MemoryMiddleware` 每次把它放进系统提示，不经过这份索引。

## 第二步：用户说“记住”，模型调用 manage 工具
用户说“以后都先给最小例子”时，模型调用 `manage_user_memory`。它是 LangMem 官方 `create_manage_memory_tool` 的产物，`ManageMemoryTool` 读取它真实的参数结构（`MemoryNote(description, content)`），接进本项目同一套工具声明、权限检查和结果保存流程；`MemoryToolGate` 让它不需要审批。
LangMem 把 create/update/delete 变成对 `BaseStore` 的 put。底层 `MarkdownMemoryStore` 只实现 LangMem 用到的 get/put/search：put 落到 `write`，在作用域目录的锁里检查后写一个 `<id>.md`（frontmatter 是 description 和 updated）。检查由 `check_memory_write` 统一做：描述是一行非空文字，描述加正文不超过 2000 字，每个作用域不超过 50 条，疑似密钥直接拒绝。模型不能用 `write` / `edit` 直接写记忆目录。

## 第三步：压缩被采用后，后台整理一次
用户不一定主动要求记住，所以还有后台整理。它只在压缩被采用时触发：`SummaryService.adopt` 成功后调用 `MemoryService.compacted`，后者在没有正在跑的整理时开一个后台任务；另有手动 `/memory extract`。run 结束时不触发。
`consolidate` 从会话里取最新摘要和有限的最近对话，`ConfiguredMemoryUpdater` 打开独立后台模型（关闭 thinking，因为 LangMem/trustcall 会强制 tool_choice），交给 LangMem 的 `create_memory_store_manager`。新增、合并、删除哪些条目由 LangMem 决定；写入仍经过同一个 `check_memory_write`，被拒绝的条目跳过并记日志。后台失败只记日志，不影响主任务。

## 第四步：记错了，用户直接改文件
`/memory` 列出索引，`/memory edit ID 内容`、`/memory delete ID`、`/memory clear` 直接修改或删除对应的 md 文件，走同样的写入检查。同一个 ID 在两个作用域都有时用 `--scope` 指明。没有变更日志和撤销；文件就是唯一的数据。旧格式的记忆文件不迁移。
## 框架在刚才的故事里做了什么
三条路径各用各的框架：Deep Agents `MemoryMiddleware` 处理 AGENTS.md；LangMem 的 manage 工具供主模型主动写；`create_memory_store_manager` 供后台整理。它们共享同一个 `MarkdownMemoryStore`（实现 LangGraph 的 `BaseStore`）。文件格式、锁、写入检查和索引是项目补上的。
## 查找：文件与字段
| 文件或结构 | 保存什么 |
|---|---|
| `~/.pycode/memory/<id>.md` | 用户记忆，frontmatter 有 description、updated |

## 遇到异常时，程序怎么处理
**off 是否把已有记忆删掉？** 不会。off 去掉索引、manage 工具和后台整理，文件还在；clear 才删除。
**后台抛异常会让用户本轮失败吗？** 不会。`background` 捕获并记日志；关闭会话时等待任务退出。
**写满 50 条怎么办？** 新增返回 `memory_limit_reached`，模型需要先合并或删除旧条目。
## 面试常见追问
- **为什么不自动召回？** 索引只占几十行，模型自己判断要不要读，和 Skill 一样；省掉了打分模型和每轮的召回请求。
- **LangMem 和 pycode 各负责什么？** LangMem 决定条目内容和合并；pycode 控制文件格式、时机和写入检查。
- **为什么不盲重试后台整理？** 一次整理可能已经写了部分文件；零重试、只记日志，不隐式重复修改。
